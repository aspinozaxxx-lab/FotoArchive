# Дополнительный сервер FotoArchive

Windows продолжает вести SQLite и LanceDB; сервер возвращает результаты тех же версий SigLIP 2, YuNet/SFace и Qwen3-VL. Результат содержит версию исходного файла, модели и сведения о GPU. Проверка версии и актуальности файла перед записью защищает каталог от устаревших ответов. Прерванные задания возвращаются в сохраняемую очередь.

На панели «Обработка» независимо включаются «На этом компьютере» и «На сервере». Переключатели относятся к фоновому распознаванию; чтение папок, метаданных, миниатюр и пользовательский поиск остаются доступны. Общая пауза останавливает обе очереди. Текущий локальный расчёт завершает снимок, затем освобождаются модели. Удалённый процесс прекращается целиком.

## Подключение и изоляция

- HTTP слушает только `127.0.0.1:18765` на сервере. Приложение создаёт SSH-туннель через настроенный пользователем псевдоним `gpu-mlserver`.
- Каждый запрос требует отдельный случайный bearer-токен. Локальный файл: `D:\FotoArchiveData\remote-token`; серверный: `/data/fotoarchive/service-token` с правами `0600`. Токены не входят в репозиторий и журналы.
- Отдельные пользователь `fotoarchive`, окружение `/opt/fotoarchive/venv`, код `/opt/fotoarchive/app` и данные `/data/fotoarchive`. Драйвер, системный Python, Docker, MLSystem2 и существующие службы не изменяются.
- `fotoarchive.service`: максимум 24 ГБ RAM, восемь CPU, низкий приоритет CPU/диска, отдельная группа процессов, запрет core dump. GPU-модели загружаются только дочерним процессом.
- `prepare.sh` и `download_models.py` выполняют только установку отдельного окружения и загрузку закреплённых моделей, без инициализации GPU. Перед установкой на другой сервер замените список заранее проверенных маленьких постоянных GPU-процессов в unit-файле; неизвестные процессы всегда имеют приоритет.

## Ожидание, кэш и жизненный цикл

Другие вычислительные процессы, включая обучение с временной нулевой загрузкой GPU, блокируют начало распознавания. При появлении новой сторонней задачи наш процесс и его дочерние процессы завершаются. Два ранее проверенных постоянных сервиса Triton разрешены только пока занимают менее 1 ГБ каждый. Их перезапуск с новым PID также блокирует FotoArchive до повторной проверки конфигурации.

Графический интерфейс подтверждает жизнь каждые 80 мс. Отдельный поток продлевает серверную аренду каждые две секунды, если интерфейс отвечает, процесс работает и очередь включена. Если интерфейс не отвечает шесть секунд, продление прекращается. Срок аренды — 20 секунд; серверный сторож проверяет её раз в секунду. Штатная пауза/закрытие освобождает GPU сразу после доставки запроса; авария, потеря питания или сети — после истечения аренды (ориентир до 30 секунд с последнего ответа окна). Удаляется только собственная группа процессов. При аварии самого сервиса systemd и Linux parent-death signal завершают оставшиеся дочерние процессы.

До 8192 снимков или кадров могут заранее ожидать на сервере, даже пока GPU занята; отправка приостанавливается при заполнении активным запасом 90% дискового лимита. Подготовка и передача идут по одному входу с очередью не более 64 небольших записей. Координатор выделяет на пополнение до 15 мс за проход. Приём результатов и подтверждение записи выполняет отдельный поток; длинная подготовка RAW не задерживает готовые результаты. На диске нет JPG/PNG с личными фотографиями: входные данные находятся в `.facache` с заголовком и сжатием. Это служебная упаковка, **не шифрование**; содержимое восстанавливается только в памяти рабочего процесса. Портреты и результаты сохраняются в сжатых записях SQLite. Трафик передаётся через SSH.

Контрольная сумма позволяет использовать уже загруженный снимок для всех требуемых операций. JPG/PNG/WebP передаются без изменения пикселей; BMP и другие декодируемые изображения упаковываются без потерь. RAW и видео используют те же подготовленные превью/кадры, что и локальная обработка; целые видеофайлы не пересылаются. Метаданные места извлекаются локально и при необходимости превращаются в географический текстовый эмбеддинг на сервере.

Лимит входного кэша и сжатых результатов — 20 ГиБ (в интерфейсе «ГБ»). Модели, среда и служебные страницы SQLite хранятся отдельно от этого учёта; суммарный объём остаётся существенно ниже разрешённых 200 ГБ. Старые завершённые записи вытесняются. Очередь активного сеанса, текущий расчёт и ещё не подтверждённые результаты закрепляют входные данные. На одно изображение допускается до 64 МиБ исходного транспортного содержимого. Более крупные файлы остаются для локальной обработки. Ошибка одного файла не останавливает пополнение всей очереди.

## Что означают показатели

Два одинаковых блока показывают успешно записанные в локальную SQLite этапы: поиск, лица, описания и места. Это операции над снимками/кадрами, а не число найденных лиц. Счётчики относятся к текущему запуску; `/мин` — количество таких операций за последние 60 секунд. Ошибки и повторное подтверждение уже готового этапа не увеличивают успешный счётчик. При перезапуске отчёт начинается с нуля, выполненные результаты в каталоге сохраняются.

В «Заданиях сервера» одно задание соответствует входному снимку/кадру и всем назначенным ему этапам. «Завершено» учитывает только полностью успешные задания. «В каталоге» увеличивается после подтверждения записи клиентом; получение HTTP-ответа само по себе подтверждением не является. Частичные, ошибочные и устаревшие результаты отмечаются отдельно. Сохранённые результаты можно искать сразу, не дожидаясь окончания очереди. Повтор одинакового содержимого использует готовый серверный результат; один такой результат может заполнить несколько записей каталога. Поэтому число этапов и число уникальных серверных заданий не обязаны совпадать. Накопленные итоги заданий не уменьшаются при вытеснении старого кэша.

«Сейчас» — скорости отправки и получения полезных данных за последние 10 секунд; «За запуск» — накопленные объёмы, без накладных расходов SSH. Отправка учитывается по мере чтения сетевым клиентом порций данных, а не скачком после всего файла. Показатель диска — занятое пространство и лимит; это не видеопамять. GPU и видеопамять относятся ко всему устройству, включая другие задачи.

## Проверки

`pytest tests/test_remote.py tests/test_preview_buffer.py tests/test_stack_viewport.py` проверяет очередь, повторы, версии файлов, аутентификацию, непросматриваемую упаковку, лимит кэша, предзагрузку и отсутствие пустого кадра стопки. `server/validate_lifecycle.py` на Linux проверяет реальное завершение дочерних процессов при паузе, потере аренды, сторонней задаче и ошибке GPU-опроса, без занятия GPU.

Первое выполнение каждой ONNX-модели сохраняет профиль и требует реальных CUDA kernel events; затем профилирование выключается, чтобы журналы не росли с архивом. Для Qwen обязательны подтверждение выгрузки всех слоёв на GPU и CUDA для визуальной части. Скрытого перехода всей обработки на CPU нет.
